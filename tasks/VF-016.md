# VF-016 - Explicit reset of an agent draft to a versioned base preset

Status: planned; implementation and all application checks unexecuted.
Product repository: `Maksym322/voice_agent`.
Planning base: `639c72a2e72f78d5b4e89560041b0d38a3d25dd0` (integration branch `vf-003-voice-playground`).
Source backlog item: owner request, 2026-10-22, reusable core and removable customization.
Outcome: an operator can inspect a known base preset and explicitly restore one agent's draft to it without losing accounts, history, published configurations, or the currently running configuration.

- Existing versioning and browser voice provide a foundation, not a completed integration SDK, business example, evaluation runner, or fully accepted release.

## Scope and design contract

1. Add one small, checked-in, secret-free base preset with stable ID and explicit preset version, separately versioned from `AgentConfig.schema_version`. Store its complete normalized `AgentConfig` payload so changing code defaults cannot silently change that preset version. Use neutral instructions without business tools, the existing UI's explicit Google/gemini-3.5-flash-lite pair, and existing schema defaults for remaining fields. Document all providers/models and required references; availability is not implied by the preset. Do not change old API defaults or rewrite existing agents. No provider request is required to inspect or reset a draft.
2. Expose the preset through an authenticated read endpoint and show the exact preset version and resulting configuration, including provider/model, before applying it. Missing or invalid preset content fails clearly and performs no mutation; no file watcher or implicit fallback overwrites database drafts.
3. Add `POST /api/agents/{agent_id}/reset-to-base` accepting the selected preset ID/version. Require the existing same-origin/CSRF policy, admin/operator edit permission, and current `If-Match` draft revision. Lock the agent row as other draft mutations do. Replace only `Agent.draft`, increment its revision once, and append a sanitized `AuditEvent` identifying actor, preset/version, and resulting revision. Preserve the agent ID/name. Repeated requests with the stale revision return 409 rather than silently applying twice.
4. Add an explicit editor action with a confirmation explaining that the saved draft will be replaced and active configuration/history remain unchanged. Cancelling sends no mutation. On success refresh the editor and show “Draft reset; publish and activate separately.” A conflict preserves unsaved text and requires reloading/reconciling; never automatically retry with a newer revision.
5. Preserve existing publish and binding operations as separate actions. A new reset draft does not require that its providers are configured until existing publish/voice validation rules require them. Do not weaken those rules or make paid calls.
6. Update configuration/user documentation and task acceptance notes. Record whether a migration is actually necessary; prefer existing draft/audit storage rather than introducing a second configuration engine.

Before confirmation offer an explicit download of the current validated saved
draft using the existing secret-free configuration format. Distinguish saved and
unsaved editor content; warn that reset replaces the saved draft and that unsaved
editor text must be saved/exported or deliberately discarded. Cancelling retains
both. Verify the downloaded pre-reset configuration can be imported with normal
revision fencing to restore the customization after a reload. Do not claim the
metadata-only audit event is an undo snapshot, and do not store full instructions
in audit logs. A persistent draft-history subsystem is outside this bounded task.

Excluded: deleting `.env`, volumes, tables, users, agents, or session data; a factory wipe; global branding/installation reset; arbitrary scripts, executable plugins, file overlays/watchers, hot loading, automatic publication/activation, SaaS tenants, deployment, or real calls. “Reset to base” means one agent's configuration draft, not the whole server.

## Manual acceptance

1. Use a clearly labelled disposable installation, synthetic admin/operator/viewer accounts and a synthetic agent with customized instructions/branding. Publish and bind its initial version; seed a labelled synthetic session plus event/diagnostic through test fixtures without real voice providers. Record IDs and aggregate counts.
2. Open the editor, inspect the preset/version and provider/model, cancel reset and verify the draft remains customized. Confirm reset and verify only the saved draft changes. Refresh/restart and verify the result persists; the prior active version and historical session remain visible.
3. In a second tab save an edit, then try reset with the stale first tab. Expect a conflict with unsaved text preserved. Verify viewer access cannot mutate through either UI or direct API.
4. Explicitly publish and activate the reset draft. Verify the synthetic existing session remains pinned to the old version. Export the old version and perform normal binding rollback; both remain possible.
5. Keep screenshots/results free of credentials. Owner acceptance remains pending until performed. Cleanup only the uniquely identified disposable stack/volume owned by this test; never the home database.

## Risks and limitations

Reset replaces customized draft instructions; confirmation and revision fencing are required. A base provider choice may lack local credentials: show it before reset, do not switch providers silently. Configuration reset must never become a data recovery mechanism. Real audio and external tools remain separate acceptance work.
