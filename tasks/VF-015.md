## Scope

1. Make History and Logs visibly refreshable and automatically refresh the
   current result page at a bounded interval while it is active. Preserve
   selected filters, cursor and selected detail; stop timers on exit/unmount.
   Prevent late responses from older filters/pages overwriting newer results.
2. Clearly explain that Board is recent/live activity, History contains saved
   completed/failed voice sessions, and Diagnostics contains sanitized errors.
   A successful session with no diagnostic must not look like an unsaved test.
3. Ensure each visible History row opens its persisted session with pinned
   version, status/times, conversation/events and diagnostics using existing
   authorized APIs. Do not invent transcript text or imply audio recording.
4. Add meaningful loading/error/empty states: distinguish no matching records
   from a failed request, show relevant active filters and offer a clear reset
   to the first unfiltered page. Refresh must preserve filters unless reset is
   explicitly chosen. Keep existing cursor pagination correct.
5. Explain retention accurately in the UI/docs: default 30 days, configured per
   published snapshot; zero means purge after ending/cleanup at the next sweep.
   Do not silently change retention or recover already purged rows. Use a
   row-specific deadline only if derived from an authorized server response;
   a short general explanation is sufficient for this task.
6. Extend scripts/check_startup.py's disposable regression with synthetic users,
   an agent, immutable version/binding, successful and failed terminal sessions,
   transcript/event rows and a sanitized diagnostic. Assert unchanged IDs and
   values after API/web restart, DB restart, container recreation with the same
   named test volume and a second migration-to-head run. Query authenticated
   History/events/logs afterward. Do not bootstrap or truncate between phases.

Excluded: database resets, account management, changing existing retention
policy, new process-log aggregation/search, recordings, analytics/report runners,
paid calls, provider setup, deployment, merging or acceptance of other tasks.
No migration or breaking API change is expected.
