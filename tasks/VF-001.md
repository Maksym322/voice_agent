# VF-001 — Foundation

Status: implementation ready for owner acceptance; hosted CI and clean-checkout
verification pending repository setup. See `docs/vf-001-acceptance.md`.

Goal: reproducible local startup of the API, dashboard, and database.
Prerequisites: check Docker, Git, and runtimes; document the selected stack,
versions, authentication approach, and commands.

Implement apps/api, apps/web, apps/voice-worker, database migrations,
.env.example, Docker Compose, basic authentication/authorization, and CI.
The worker may initially be an explicitly labeled scaffold without voice logic.

Acceptance criteria:
- A clean checkout starts using the README instructions.
- Migrations apply to an empty database.
- Protected API endpoints reject unauthenticated requests.
- No default production password is provided.
- CI runs linting, type checks, and relevant tests without paid APIs.

Manual verification: start the application, sign in, sign out, and verify
that protected access is denied after sign-out.
Out of scope: real voice sessions, telephony, and client integrations.

### Proposed implementation choices, not confirmed decisions

These are a concrete candidate implementation, not an amendment to
`docs/decisions.md`. Resolve stack and authentication choices before dependent
implementation; record the actual agreement and versions during VF-001.

- Adopt the existing Python/FastAPI, React/TypeScript, PostgreSQL, and Docker
  Compose proposal. Use a root uv Python workspace for API/worker and a root npm
  workspace for the dashboard. Use SQLAlchemy/Alembic for database migrations.
- Select mutually compatible supported runtime, framework, database, and tool
  versions from official documentation during implementation. Record exact
  versions and documentation links; pin package dependencies and container
  versions/digests and commit lockfiles. Installed versions below are observations,
  not selected versions or compatibility evidence. No version selection was made
  in this planning pass.
- Use local accounts with a vetted password hashing library and opaque,
  server-side sessions. Login issues an HttpOnly, SameSite cookie; production
  requires Secure cookies. Apply CSRF protection to cookie-authenticated mutations.
  Logout revokes the server session so replaying the old cookie is denied.
  External identity providers and account recovery are outside this foundation.
- Provide an interactive local administrator bootstrap command; require the
  owner to supply credentials, hash passwords, and never embed a default password.
  No public registration or user-management dashboard is required.
- Serve the dashboard and API under one documented local origin. Proposed API:
  `GET /health/live`, `GET /health/ready`, `POST /api/auth/login`,
  `POST /api/auth/logout`, `GET /api/auth/me`, and
  `GET /api/admin/health`. The last endpoint supplies a minimal admin-only
  diagnostic to exercise authorization without implementing VF-002.
- Proposed permission matrix: all authenticated roles may read their own identity
  and use the foundation dashboard; only admin may read the admin diagnostic.
  Missing/invalid/expired/revoked sessions return 401; a valid session lacking the
  role returns 403. Never accept role or identity claims supplied by the browser.
- Proposed CI target: GitHub Actions on pull requests and pushes, using a disposable
  PostgreSQL service and the same checks as local development. Creating workflow
  files is in scope; connecting GitHub, publishing, or pushing is not.

## Manual acceptance (pending implementation and owner execution)

All commands here are proposed README interfaces and currently unavailable.
Use only synthetic accounts and fresh local credentials. Record the actual
revision, selected versions, expected/actual results, and any failures.

1. **M1 - Clean setup and migrations.** In a fresh checkout, use the documented
   runtime versions and a running Docker daemon. Copy `.env.example` to ignored
   `.env` and fill required values locally. Under a unique Compose project
   (set `COMPOSE_PROJECT_NAME=vf001-acceptance`), run
   `docker compose build`, `docker compose up -d db`, and
   `docker compose run --rm api alembic upgrade head` twice.
   Both migration runs must exit zero; the second must preserve schema/data.
   Run proposed interactive
   `docker compose run --rm api python -m voice_fleet_api.admin create-user --role admin`.
   Enter synthetic credentials at prompts, never in command arguments.
   Verify there was no usable account before this explicit bootstrap.
2. **M2 - Start and sign in.** Run `docker compose up -d` and inspect
   `docker compose ps`. Open the README URL, sign in, and confirm the dashboard
   shows the signed-in identity. Check readiness and the explicit worker scaffold
   message. No provider keys or live voice response should be needed.
3. **M3 - Negative access.** In a private browser, open the protected dashboard
   directly; it must require sign-in. Call `GET /api/auth/me` without a cookie
   and with an invalid cookie; expect 401 and no protected data. Try a wrong
   password; expect a generic error and no session. Send an authenticated mutation
   without required CSRF protection; expect rejection and unchanged state.
4. **M4 - Sign out and replay.** Keep a test session cookie only in temporary
   local browser/client memory. Sign out, reload/directly revisit the dashboard,
   and retry `GET /api/auth/me` with the previous cookie.
   Expect sign-in in the browser and 401 from the API, including cookie replay.
   Remove the temporary cookie; do not include it in reports.
5. **M5 - Roles.** Use the same proposed interactive bootstrap command with
   `--role operator` and `--role viewer` for synthetic users.
   Each can read `/api/auth/me`; both receive 403 on `/api/admin/health`.
   Admin receives 200. Adding a role field/header to the lower-privilege request
   must not change its permissions.
6. **M6 - Failure and persistence.** Using only the disposable acceptance
   installation, omit required credentials and verify a clear startup/bootstrap
   failure without secret leakage. Stop its database and verify readiness fails
   and migration exits nonzero. Restore the database/settings, then run
   `docker compose down` and `docker compose up -d` without volume deletion;
   the bootstrapped user must still be able to sign in.
7. **M7 - Checks and cleanup.** Run Q1-Q6 after their documented test setup and
   inspect results, including skipped/failed checks. Review the CI workflow and
   a hosted run when available; do not infer a hosted pass from local results.
   Stop the acceptance project with `docker compose down`.
   Only for the uniquely named disposable project, use
   `docker compose down --volumes` if deleting its synthetic data is intended;
   never apply this cleanup to an existing installation. Remove local temporary
   secrets/test fixtures and retain only sanitized evidence.
