# VF-017 - Portable, validated client agent configuration package

Status: planned; blocked on accepted VF-016; implementation and all application checks unexecuted.
Product repository: `Maksym322/voice_agent`.
Planning base: `639c72a2e72f78d5b4e89560041b0d38a3d25dd0`; implementation base must include accepted VF-016 and persistence fixes.
Source backlog item: owner request, 2026-10-22, reusable foundation with independent client customization.
Outcome: export one selected agent's reviewed configuration from installation A and explicitly import it as a draft in independent installation B, without copying users, history, credentials, database IDs, or active bindings.

## Context and dependencies

- VF-016 must be accepted and integrated first; record its exact commit and reset tests before starting. Recheck the actual persisted configuration contract rather than assuming a planned API exists.
- Existing `GET /api/agents/{id}/versions/{version_id}/export` already exports a validated immutable agent snapshot. Existing import validates and replaces one draft with revision checking. Reuse these behaviors; do not duplicate them behind an unrestricted package loader.
- Follow `AGENTS.md`, `docs/product.md`, `docs/architecture.md`, `docs/decisions.md`, `docs/configuration.md`, `docs/integrations.md`, `docs/testing.md` and `docs/workflow.md`.
- The `client.yaml`, knowledge/deployment directory tree and integration SDK described in architecture are not complete executable features. This slice deliberately implements a single-agent JSON package; it must be labelled as such and must not claim a full business integration, installable module, working booking workflow, or complete client deployment.

## Scope and proposed minimum contract

1. Document and implement one bounded JSON envelope: `package_schema_version: 1`, optional bounded display name, `base_preset` with stable ID/version from VF-016, and one fully materialized `agent_config` validated by the existing `AgentConfig` schema. The materialized configuration is authoritative; do not introduce patch merging, recursive overlays, or behavior depending on files remaining present. Base provenance is informational and must not change reset semantics. Reject unknown envelope fields and unsupported versions. Set a documented request/file size limit before parsing.
2. Export a specifically selected published version through authenticated UI/API; show which version is exported. Export only the envelope and supported agent fields: instructions, locale/timezone, voice provider/model/voice IDs, provider reference names, tool/module allowlists, per-agent branding, session limit and retention setting. Preserve only fields actually implemented by `AgentConfig`; do not manufacture organization provisioning, global theme application, knowledge uploads, integration adapters, secret resolution, or deployment manifests. Explicitly label declarative module/tool names as configuration, not installed capabilities.
3. Import into a specifically selected existing agent as a draft, using admin/operator permission, existing origin/CSRF protection and `If-Match` revision. Show the validated complete configuration and current target before confirmation. After confirmation, apply atomically under the normal agent row lock, increment revision once and write a sanitized audit event. Reuse normal validation and error conventions; no partial mutation, auto-create users, auto-publish, auto-activate, auto-call, or auto-install.
4. A package contains only `env:NAME`/`secret:NAME` references, never resolved values. Do not read `.env`, process secret values, credentials, cookies, password hashes or session transcripts while exporting. Reuse/strengthen existing credential-like-value rejection without promising perfect free-text secret detection. Refuse raw credential fields/values and avoid echoing their content in errors/logs. Package text is user-provided data; never execute it, open a package-specified path/URL, interpolate commands, or install a module.
5. Imports do not require external credentials to be available merely to store a draft. Present required provider reference names and explain that installation B must configure its own secrets separately. `secret:` remains a reference format, not a new implemented secret-store integration. Missing runtime credentials must retain the normal safe startup failure behavior; do not copy or invent credentials.
6. Keep current bare `AgentConfig` import/export backward compatible. Add distinct package controls/endpoints or an unambiguous explicit format selection; never silently reinterpret a package as plain AgentConfig or overwrite a UI draft on startup/file change.
7. Add a reproducible disposable two-installation acceptance runner extending `scripts/isolated_stack.py` with separate projects, volumes, ports, environments and synthetic users. Document supported package version, exact fields, retention semantics, secret setup boundary, and unsupported future features in `docs/configuration.md` and a short client setup guide. No production rollout is included.

Excluded: full-directory archives/YAML loaders, file extraction, arbitrary file or network access, executable plugins, integration SDK/booking, shared tenancy, account/data export, database cloning, phone inventory/trunks, live calls, automatic provider model discovery, global branding migration, deployment or cleanup of any existing installation.

## Manual acceptance

1. Start the new two-stack runner in its documented owner-preview mode (mode/command must be implemented and documented). It must print two clearly labelled URLs and synthetic credentials, identify disposable lifetime and safe cleanup scope, and keep both available for owner inspection. No real keys are supplied.
2. In A, create a synthetic branded agent, publish and export a selected version. Inspect the JSON: only documented configuration and reference names exist. In B, create a different account/target agent and retain a synthetic history fixture; preview import and cancel once, then confirm. Verify no binding appeared and the existing history/account remain.
3. Change B's instructions/branding, refresh and restart B. Verify persistence and A's unchanged configuration. Reset B's draft to the VF-016 base; verify both installations' accounts/history and B's prior published/active version remain intact.
4. Try malformed JSON, a future package version and a fake raw API key field. Expect sanitized errors and no writes. Attempt as a viewer and from a stale second tab; expect rejection without overwrite. Existing plain AgentConfig import/export still works.
5. Owner acceptance is separate from the automated runner. Clean only the runner's explicitly owned disposable projects/volumes after inspection; do not delete any home/install data. Report that these synthetic checks do not establish live audio or a business integration.

## Risks and unresolved questions

Per-agent branding is not deployment-wide branding; unsupported global configuration remains out of scope. Provider model availability may differ between installations: validate the supported schema, show requirements, never substitute models silently. Free-text instructions can contain personal data; exporting them is an explicit operator action and the UI must state the package includes those instructions. The package is a portable configuration, not a backup or a complete custom product fork.
