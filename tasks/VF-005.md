# VF-005 — SIP telephony and phone routing

Status: in progress. Bounded outbound test and provider-neutral inbound
inventory/routing code are implemented in the isolated working copy. Carrier
delivery, real phone calls, and full owner acceptance remain.

## Goal

Use the existing pinned voice worker and session board for real phone calls.
One session ID represents one call. A provider call ID is stored separately.
The owner wants both inbound calls on a Ukrainian +380 number and individual
outbound calls. Campaign dialing is outside this task. The outbound test code
uses a provider-neutral LiveKit trunk ID, but the owner's Twilio account
requires a $20 upgrade and does not allow a trial SIP trunk. On 2026-09-28 the
owner relaxed the earlier $5 cap for a test and considered paid Twilio with a
foreign voice number. The carrier decision was later postponed; long-term +380
inbound service remains undecided.

The owner registered a Zadarma account. Official Zadarma AI integration guides
describe outbound SIP through `pbx.zadarma.com` with PBX extension credentials
and inbound forwarding to an external SIP URI. This is the next candidate;
actual LiveKit interoperability and the owner's checkout total remain untested.

## Acceptance criteria

- An admin explicitly starts one outbound call to a server-configured +380 test
  destination. Operators and viewers cannot start it, and callers cannot submit
  arbitrary destinations. No call starts during page load or ordinary checks.
- The callee hears the pinned agent speak, can reply and interrupt, and both
  transcript sides, events, metrics, and a masked destination appear under one
  phone session card. A new agent publication cannot change that call.
- Answer, decline/no-answer, SIP failure, hangup, sign-out, and duration expiry
  produce accurate server states and release the LiveKit room. The provider call
  ID is not used as the session ID.
- A separately chosen +380 provider routes real inbound calls through LiveKit
  SIP to the correct active agent. A number is a reusable routing resource and
  can carry multiple sessions subject to actual trunk and worker capacity.
- Admins can manage number inventory and routing; server authorization and
  canonical statuses remain authoritative. The board and history show actual
  calls only, with phone identifiers masked by role.
- Automated checks use synthetic SIP substitutes and a disposable database.
  Real billed calls are separate manual acceptance with a configured spend cap.

## First-slice configuration

`OUTBOUND_SIP_TRUNK_ID` references a stored LiveKit outbound trunk.
`OUTBOUND_TEST_DESTINATION` is a single +380 E.164 number in ignored `.env`.
`OUTBOUND_TEST_MAX_SECONDS` defaults to 180 and is combined with the published
agent and server limits. The destination is not accepted in the HTTP request.
Provider credentials live in LiveKit trunk configuration, not in product exports.
See `docs/sessions.md` and `docs/live-setup-and-cost.md`.

## Manual acceptance for first slice

1. Choose a carrier that can terminate a call to the owner's own +380 number,
   confirm its Caller ID and Ukraine dialing rules, then configure a stored
   LiveKit outbound SIP trunk. Review the carrier's funding and per-minute
   charges before the manual test. Twilio and Zadarma remain candidates; no
   provider is required by the application code.
2. Set the trunk ID and your own +380 destination in ignored `.env`, restart API,
   and sign in as admin. Publish and bind a voice agent.
3. In Agents choose that agent and click **Call test phone** once. Answer the
   call, hear a greeting, speak, interrupt, and hang up. Verify the session ID,
   masked destination, both transcripts, and room cleanup in the board/history.
4. Repeat with a declined call and with an unavailable trunk. Check error
   records and cleanup. Verify operator/viewer and missing CSRF are denied.

The outbound audio path and provider interoperability are unaccepted until this
manual test passes. Do not treat an API substitute as a connected phone call.

## Inbound preparation without a carrier decision

The implementation can provision a LiveKit trunk and individual dispatch rule
after a real number and the carrier's documented SIP origination CIDRs are
known. Admin inventory and route editing use server authorization, revision
checks, and active-agent validation. A newly dispatched call creates its own
session ID and pins the current published version. The carrier's delivery to
the LiveKit SIP endpoint and actual audio must be verified separately. No
number is shown as connected merely because the route exists. The owner can
postpone Twilio or +380 provider selection without blocking browser voice,
console development, or this code path.

An admin can deactivate a configured route when no call on that number is
pending or active. The worker blocks new dispatches before LiveKit cleanup;
failed cleanup remains retryable. A retired number keeps its history and can be
reactivated with new LiveKit resources. Carrier delivery still requires a real
call after every provisioning change.
